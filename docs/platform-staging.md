# Platform staging smoke

This story keeps a staging equivalent locally and in CI and tracks the Railway IaC graph applied to the synthetic production pilot on 2026-10-22. Do not connect customer traffic, real photos, Pix or image generation to these endpoints. The current provider state and deployment follow-up are recorded in [the Railway setup runbook](./railway-pilot-setup.md).

For account creation, workspace cost approval, step-by-step Railway setup, environment variables, Bucket handling, and Danillo's replication checklist, follow [Railway — configuração inicial do piloto](./railway-pilot-setup.md).

## Run

Install Node 24 and Docker Compose. Run `npm ci`, `npm run check:boundaries`, `npm run build`, then `npm run smoke:local`. The smoke script creates an ephemeral secret, starts private PostgreSQL and the web process, then exercises a worker crash after the synthetic effect commits but before queue acknowledgement. The restarted worker receives the same job and the destination retains exactly one effect for its task ID. It also exhausts the bounded automatic retries, queries the safe terminal failure code, manually recovers the same failed job, and checks that the recovered task still has one effect. Unauthorized access, invalid recovery, and database loss are checked before the local volume is removed. Test-only crash/failure flags are read only when `STAGING_SMOKE_TEST_MODE=1` and only for synthetic jobs. The script uses port 3000 on localhost. All test data is synthetic.

### Local synthetic backup and restore

Install Node 24 and Docker Compose, then run npm run backup:restore:local. The command requires a local Docker context and uses the same localhost port 3000 as npm run smoke:local; run them sequentially. It creates two uniquely named Compose projects with separate PostgreSQL volumes and ephemeral credentials. With the source worker stopped, it writes a full custom-format PostgreSQL dump to a temporary local directory, restores it into the second project, queries the original task UUID through the restored API, starts the restored worker, and confirms that the task and pg-boss job complete with exactly one synthetic effect. It also confirms that the source task remains queued with its job intact and no effect. The command attempts to remove both projects and the dump on every ordinary exit; cleanup failure returns nonzero and identifies the remaining project. No dump is sent to an external service.

This exercise proves only the local synthetic restore path. It does not configure a provider backup, schedule, destination, encryption or access policy, nor set retention, RTO or RPO. External backup configuration remains gated on approval of a provider and its operational/privacy controls.

For manual operation, provide `POSTGRES_PASSWORD` and a random `STAGING_SMOKE_SECRET` of at least 32 characters, then run `docker compose up -d --build`. POST `/api/internal/smoke` with `Authorization: Bearer <secret>` and no body. The 202 response includes `id`. GET `/api/internal/smoke/<id>` with the same header to view `queued`, `processing`, `completed` or `failed`. To recover, POST `/api/internal/smoke/<id>/retry` with the same header. Recovery returns 202 only for a task and queue job both in terminal `failed`; missing tasks return 404, active or otherwise ineligible tasks return 409, and an invalid secret returns 401. Every response disables caching. Database failure returns 503 without an acceptance ID.

Only the web process binds a host port, and only to `127.0.0.1`. PostgreSQL has no host port. In an external environment, put webhooks behind HTTPS, keep the database on a private network with no public ingress, and restrict internal endpoints at the network edge. Store staging and production secrets in separate provider scopes; never reuse local or CI secrets. Private responses must keep `Cache-Control: no-store` and bypass shared caches. Consumer media for E6 must use private storage; queues and logs keep references, never image bytes. The database contains only UUID correlations, state and timestamps; queue payloads contain a synthetic marker. Logs contain no credential, personal data or media bytes.

## Platform isolation preflight

Run `npm run check:platform-isolation` locally and in CI. It checks the repository-controlled Compose bindings and network, Docker build exclusions, local environment placeholders, and private route cache policy without requiring Docker. The local CI workflow runs this check and the synthetic smoke only; it does not provision or deploy an external service.

This preflight cannot prove that a live provider has distinct staging and production secrets, public HTTPS, private database ingress, a shared-cache bypass, or private E6 media storage. The Railway graph in `.railway/railway.ts` describes one production web service, one internal worker, private PostgreSQL, and a private IAD Bucket. It uses the approved `us-east4-eqdc4a` service/database region and a private `DATABASE_URL` reference. The worker, database, and Bucket have no public domain, and the Bucket credentials are not linked to either service because no media path is enabled.

## Provider backup and isolated restore

Native volume snapshots and PITR were not enabled because Railway requires the Pro plan for scheduled/manual snapshots. The owner approved a Hobby-compatible cron service every three days at 03:00 UTC (`0 3 */3 * *`), writing logical dumps to a private IAD Bucket with six-day retention. One manual backup (48,394 bytes) and one isolated restore to a disposable private PostgreSQL service succeeded on 2026-10-22. The first naturally scheduled run and end-to-end RTO remain pending. This is a synthetic pilot policy; add an off-project copy and review access/retention before storing real customer data.

The local `npm run backup:restore:local` command proves only local synthetic backup/restore behavior. It does not prove a Railway schedule, backup retention, provider access policy, or recovery time. After the isolated provider drill passed, `PRODUCTION_BACKUP_RESTORE_VERIFIED=true` was recorded in the production web service; the other five approval flags remain absent.

The task and job enter PostgreSQL in one transaction. The destination effect uses the task UUID as its unique idempotency key, and the effect row and `completed` state commit in the same transaction. Worker state transitions are fenced by pg-boss's retry count, so a delayed older attempt cannot replace a newer result. Automatic retries are limited to two retries; each manual recovery reopens the same failed pg-boss job and grants one additional attempt without changing the key or deleting the effect. Queue jobs use `deleteAfterSeconds: 0` so pg-boss retains the row for terminal status reconciliation and manual recovery. The guarantee covers this synthetic PostgreSQL destination only; it does not claim exactly-once queue delivery or cover effects outside PostgreSQL. The Railway backup and isolated logical restore are verified as described above; the local synthetic restore demonstration is separate.

## Safe operational events

The worker emits `platform_event` records for `smoke_started`, `smoke_attempt_failed`, `smoke_completed`, and task-scoped `infrastructure_error` events. Each record contains only the event type, task UUID (`correlationId`), zero-based `attemptNumber`, known state (or `unknown` when persistence could not confirm it), and an ISO `occurredAt` timestamp. Failure events use the stable codes `attempt_failed` and `infrastructure_error`; queue-level pg-boss failures retain the static `queue_error` marker. Before its first attempt, a task reports `attemptNumber: null` in its durable status. Never add job payloads, exception text or stacks, credentials, personal data, or media bytes to these events or logs.
